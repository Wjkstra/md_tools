# 性能设计：流畅编辑与长文档低负载

本文汇总 MdNote 在性能方面的设计：原生控件、WebEngine 渲染、
防抖节流、缓存策略、安装体积控制，以及实测数据与后续优化方向。

## 1. 性能目标与负载来源

| 目标 | 说明 |
| --- | --- |
| 日常输入零卡顿 | 按键处理短路径；重计算全部防抖到空闲时 |
| 排版顺滑 | 由 WebEngine（Chromium 内核）负责合成，只重绘可见区域 |
| 长文档可打开 | 块解析为线性复杂度；派生数据按需重建 |
| 内存与体积可控 | 缓存有界；打包时排除无关依赖 |

负载来源与对策：

| 负载来源 | 对策 |
| --- | --- |
| 源码长文档的语法处理 | `QPlainTextEdit` 只对可见块运行语法高亮 |
| 大文档排版 | WebEngine 合成器按视口绘制；图片懒加载 |
| 高频事件（输入、滚动） | 防抖 / 节流，统计与大纲延迟计算 |
| 重复的图表渲染 | 按图表源码缓存结果 |
| 安装包冗余 | PyInstaller 排除未使用的大型库 |

## 2. 两种编辑器的性能特征

### 2.1 源码模式：QPlainTextEdit

- `QTextDocument` 基于块（block）组织，编辑器只布局、绘制可见区域
- `QSyntaxHighlighter` 随可见块增量计算，长文档打开后滚动不会全文高亮
- 自动括号、Tab 缩进均为本地短操作，不涉及整篇文档

### 2.2 渲染后模式：WebEngine

- 排版页面由独立的 WebEngine 进程运行，不占用 / 不阻塞 Python 主线程
- Chromium 合成器只光栅化、绘制视口附近内容，滚动由 GPU 合成
- 页面中的图片统一使用 `loading="lazy"`，滚动到时才加载
- 页面 JS 仅承担块编辑交互，结构计算放回 Python，避免页面内做重逻辑

## 3. 防抖与节流

| 场景 | 策略 | 时延 |
| --- | --- | --- |
| 字数 / 统计更新 | 输入停顿后计算 | 200ms |
| 大纲重建 | 输入停顿后计算 | 300ms |
| 自动保存 | 输入停顿后写盘 | 1000ms |
| 外观 / 主题应用 | 设置变更时即时下发 | — |

这样连续输入期间不会逐字触发统计、大纲或文件写入，
只有停顿后才做一次更新。

## 4. 缓存与按需计算策略

| 机制 | 实现 | 作用 / 失效方式 |
| --- | --- | --- |
| 代码块语法高亮 | 页面端 IntersectionObserver 懒高亮 | 仅高亮进入视口（含 600px 余量）的代码块；首屏前 `CODE_HIGHLIGHT_HEAD`（8）个立即高亮 |
| Mermaid 结果 | 页面端按图表源码标记 dataset.rendered | 相同源码不重复渲染；开关设置或源码变化时重绘 |
| KaTeX | 页面端按公式 data-tex / data-md 标记 | 已渲染的公式不重复调用 KaTeX |

渲染后模式是一个连续 contenteditable 表面（见
[data-model.md](data-model.md)），结构由 Python 端 `surface_html` 平铺生成，
派生数据（字数统计、大纲）在输入停顿后才计算并比较前后差异，**无变化时跳过 DOM 更新**。

## 5. 安装体积控制

PyInstaller 打包时通过 `excludes` 排除项目不使用的大型依赖：

- `numpy`、`PIL`（图像处理）
- `tkinter`、`unittest`、`pydoc_data`

安装包体积的主要部分是 Qt WebEngine 运行时本身（Chromium 内核），
这是获得高质量 HTML/CSS 排版能力所必需的固定成本。
最终安装目录约数百 MB，其中应用自身代码占比很小。

## 6. 实测数据

以下为开发机（Windows 10，Python 3.10）上的实测结果，
数据来自自动化脚本，可重复验证。

### 大块模型解析（约 95 万字符、30,000 个内容块）

| 指标 | 实测 |
| --- | --- |
| 文本字符数 | 952,779 |
| 解析得到的块数 | 30,001（含文末挂尾块） |
| `build_model` 耗时 | **≈ 451 ms** |
| 序列化往返一致 | 是 |

解析复杂度与行数成线性关系；文末挂尾块不改变文本，
序列化结果与输入逐字符一致。

### 编辑器变换与序列化（单元测试）

- 行内 Markdown 即时转换、HTML→Markdown 反向序列化、代码编辑等用例
  全部通过，执行时间为毫秒级
- JS 用例：`node --test tests/test_md_inline.js tests/test_html_to_md.js tests/test_code_editing.js`
- Python 用例：`python -m unittest discover -s tests`（含真实 WebEngine 交互）

### 渲染后模式（WebEngine 连续表面）

- 实时模式将整篇文档平铺渲染为**一个** contenteditable 元素，选区可跨块，
  Markdown 标记在键入时即时转换
- **代码块语法高亮按需进行**：`surface_html` 不预渲染 Pygments，只输出纯文本
  镜像；页面为每个代码块安装 IntersectionObserver，滚动接近视口时才通过
  QWebChannel 调用 Pygments 高亮，避免长文档每次渲染都高亮全部代码块
- 首屏前 `CODE_HIGHLIGHT_HEAD`（默认 8）个代码块立即高亮，保证打开即见彩色代码
- 重建表面前会断开所有代码块的 IntersectionObserver，避免反复加载累积
- 图表（Mermaid）、公式（KaTeX）在 `postProcess` 中处理，均带「已渲染」标记，
  相同内容不重复计算

## 7. 超长文档的后续优化方向

当前连续表面对超长文档（万段级）的主要成本是 Python 端整篇 `surface_html`
与 QWebChannel 全量 HTML 传输。已通过去除全文 Pygments 预渲染降低开销，
仍可继续：

1. 增量提交：重渲染时只更新发生变化的块，而非整篇 innerHTML
2. 视口窗口化：区间外块替换为等高占位，滚动时经 rAF 挂载 / 卸载（保留滚动补偿）
3. 将批量解析、导出等耗时操作移入工作线程，避免阻塞 UI

## 8. 性能准则（贡献者）

- 任何「整篇文档」级别的计算都要问：能否只处理变化的部分、或延迟到空闲时？
- 新缓存**必须有界**；不要引入随文档长度无限增长的容器
- 连续输入触发的派生计算（统计、大纲、保存）一律防抖
- 图片 / 媒体保持懒加载；不要在页面启动时预加载全部资源
- 耗时任务放入工作线程，且不得在工作线程中直接操作控件
